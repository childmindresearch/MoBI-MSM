# MoBI-MSM Test Fixtures

Representative (non-production) data for exercising the participant-facing UX described in `participant-ux-spec.md`. The vignette and stance keys are the team's current versions; the assignment rows are test rows. Keep the same column schemas when swapping in real files.

## Files

**category_key.csv** — `category_label, category_name`. The 4 fixed categories, labelled with the vignette key's Intent codes: `INF` Know/Understand, `DEC` Decide/Get Advice, `REF` Reflect/Make Meaning, `SUP` Seek Support/Help.

**vignettes_appraisals.csv** — `VID, Intent, vignette_text, appraisal_text`. The vignette battery (24 per Intent). Each vignette is a short imagined situation; its appraisal is a first-person statement the participant rates on the 0–100 agreement scale. The scale is the same for every appraisal, so its 0/100 anchors ("Do not agree at all" / "Completely agree") live in `app/prompts.py`, not here. Replaces the old `scenario_key.csv`.

**stance_key.csv** — `stance_label, stance_name, system_prompt`. The 3 Stances and their system prompts.

**practice_vignette.csv** — `VID, vignette_text, appraisal_text, stance_label, ends_with_question`. The single fixed practice-block record. Not part of the assignment CSV, since it's identical for every participant per the spec. The practice block always uses the `calibrated` Stance as a neutral default, and its replies end on a question.

**assignment.csv** — `participant_id` plus 12 repeating `category_N, vignette_N, stance_N, question_N` groups. `vignette_N` is a VID whose Intent must match `category_N`. `question_N` is 1 if the LLM's replies in that block must end on a question, 0 if they must end on a statement; within each stance, two blocks are 1 and two are 0. Three test participants (TEST001, TEST002, TEST003), each with all 4 categories × 3 stances covered exactly once, using a distinct vignette for every block, in a different block order per participant. TEST003 is structurally identical to TEST001; its only purpose is to appear in `completed_sessions.csv` so the Start Screen's "already run" branch has something to test against.

**Pilot rows (PILOT_001–PILOT_016)** — also in `assignment.csv`, generated by `scripts/make_pilot_assignment.py` (fixed seed, so rerunning with `--write` reproduces them and replaces only the `PILOT_` rows). Within each participant they follow the same rules as above, plus no category or stance in consecutive blocks. Across the 16: each category appears in each block position 4 times; each position has 8 question and 8 statement blocks; each stance appears in each position 5 or 6 times; every Category × Stance cell is a question block for exactly 8 participants; and each of the 96 vignettes is used exactly twice, under two different stances, once in a question block and once in a statement block. Running the script without `--write` prints the balance report.

**completed_sessions.csv** — `participant_id, completed_at`. A stand-in for whatever session-output record the real system checks to determine if a Participant ID has already been run. Only TEST003 appears here — TEST001 and TEST002 should behave as "not yet run" at the Start Screen.

## Scaling up

The battery now has 24 vignettes per Intent, so different participants can draw different sets. The three test rows use only the first six per Intent; generating real assignment rows (vignette draws, block order, and the question split) is still the research team's task.
